# ili9341-lcd-secondary-screen

把这块 ILI9341 当桌面副屏：上位机（`../secondary-screen-desktop/`）抓 Wayland 输出的一个 320×240 区域，
按 16×16 分块 diff，只把变化的块走串口推过来，板子按块写屏。**不做整屏刷新**，
光标、时钟、窗口标题这类小改动只传几十到几百字节。

- 屏与接线：与 [`../ili9341-lcd/`](../ili9341-lcd/README.md) 完全一样（18 根 GPIO 的 16 位 8080 并口），本目录只多用到串口
- 数据链路：`esp_hal::usb::usb_serial_jtag` 的 **CDC 数据通道**，主机侧就是 `/dev/ttyACM*`（缺省 2 Mbaud 的设置对 CDC 无效）
- 板载 CH343P 的 UART0（GPIO16 = U0TXD、GPIO17 = U0RXD）与 USB CDC **同时**收帧
  （`serve_usb` / `serve_uart` 两个任务），上位机连哪个口都行；走 CH343P 时 `--baud` 必须与
  固件 `UART_BAUD`（2 Mbaud）一致，CDC 链路忽略波特率
- WiFi：板子作 **TCP 服务端**——STA 连 `R3` 热点（DHCP 取地址），监听 `TCP_PORT`（8080），
  上位机用 `--host <板子IP>` 连进来（与 `--serial` 同给就是分带并行，带宽相加）。三条链路**同时开**，帧协议完全一样，谁先连上谁推

## 协议

统一信封，多字节整数一律小端：

```text
C6 D5 | cmd(1) | len(2) | payload(len) | sum8(1)
```

`sum8` 是 `cmd` 到载荷最后一字节的逐字节和（u8 回绕）。命令分两类，板子只回控制应答：

| cmd | 类别 | 载荷 | 说明 |
|---|---|---|---|
| `0x01` | 数据 | `frame(2) \| 标志(1) \| 数量(1) \| 批号(1) \| 总数(1) \| 数量 × tile` | 一条消息一块 16×16 的 RGB565 图像（数量恒为 1），最高位标志 = 本帧最后一块；**不回任何应答**，丢了就丢了 |
| `0x02` | 控制 | 空 | 查询，板子回 `0x81`（`status = 2`） |
| `0x03` | 控制 | 空 | 清屏 |
| `0x04` | 控制 | 空 | 重置板子内部状态（帧号/进度/帧率采样），不动屏幕 |
| `0x06` | 控制 | 空 | 上位机确认收到几何信息；不确认就每 500 ms 重报 |
| `0x85` | 上报 | `width(2) height(2) scale(1)` | 板子 → 上位机：面板分辨率与采样倍数，上电后持续重发直到收到 `0x06` |
| `0x81` | 应答 | `status(1) fps(1) busy_ms(2) frame(2) tiles(2) hash(4)` | 板子 → 上位机；`frame/tiles/hash` 是板子本帧进度与数据哈希，留作诊断 |

每块 tile 的编码：

| 字段 | 长度 | 说明 |
|---|---|---|
| `col` `row` | 1 + 1 | tile 坐标（屏幕 16×16 像素一格），屏是 20×15 格 |
| 源像素 | — | 每块装 `(16/SCALE)²` 个源像素，板子把每个铺成 `SCALE×SCALE`；`SCALE` 是固件常量 |
| `kind` | 1 | `0` = 原样 RGB565，`1` = 游程，`2` = 4 色调色板 + 2bpp 索引，`3` = 16 色调色板 + 4bpp 索引 |
| `len` | 2 | 载荷字节数（小端）；原样时等于 `(16/SCALE)² × 2`，SCALE 为 1 时就是 512 |
| 载荷 | `len` | 见下 |

调色板（`kind = 2/3`）：先 `n` 个 u16 颜色（小端），再按低位在前的位序打包索引；
只在「不同颜色数 ≤ 4 / ≤ 16」时由上位机选用，所以**无损**。实测在当前桌面内容上很少触发
（每块颜色数普遍超过 16），bytes/frame 与纯游程持平（78%）。

游程（`kind = 1`）的单位是一个字节的标签：

- `0x00..0x7F`：后面跟 `n+1` 个原样像素（每个 2 B 小端）
- `0x80..0xFF`：后面跟 1 个像素（2 B 小端），重复 `(tag & 0x7F) + 1` 次

上位机对每块都算一遍，游程不短于 512 B 就退回原样，所以**任何内容都不会比不压缩更大**。

应答字段：

- `status`：`0` 处理完、`1` 校验/命令错、`2` 对查询的回应
- `fps`：板子实测的帧率（相邻两个「最后一块」的间隔），上限 30；`0` 表示还没测到或已过期
- `busy_ms`：本帧从收到第一块到画完最后一块的毫秒数，也就是**板子的处理能力**——上位机按
  `1000 / busy_ms` 的八成来定投屏帧率，余量留给链路空转，延迟才不会累积

数据不等应答（流式语义：丢了就丢了，缺块靠后续帧补），控制命令一问一答。
每条数据消息只带一块 tile：慢口一次只占一小块，丢一块的暴露窗口最小，逐块抢活不需要任何门槛。
接收槽池 64 块（每块约 0.5 KB）；收帧任务常备一块读缓冲，读完入队再从槽池补下一块——
补不到就不读，链路背压全靠这一点：USB 有流控、字节顶在缓冲里；UART 的 128 字节 FIFO
没有流控，溢出就丢，流式数据可接受。

板侧帧推进：当前帧的块直画，未来帧的块进「下一帧」缓存（最多 5 块）；当前帧的 LAST 块画完
一有新帧的块就推进（清计数、缓存块按序画掉）；缓存满 5 块说明当前帧卡住了，弃等迟到块直接推进，
之后收到的过期帧块直接丢。渲染任务取到一块就画一块（每块还让出 CPU 让收帧任务排空
FIFO），不存在攒批。推进由渲染任务单一所有者判定，无需加锁。

两边常量必须一起改：本目录 `src/link/protocol.rs` 与 `../secondary-screen-desktop/src/link.rs`、`../secondary-screen-desktop/src/frame.rs`。

## 吞吐与上限

实测（一条消息一块、无数据应答）：单 CDC 稳态约 **280 KB/s**，双口（CDC + UART0）约
**320 KB/s、板子实绘 24 fps**——双口真并行，慢口逐块贡献不拖快口；多口调度见
`../secondary-screen-desktop/README.md`。

压缩效果（实测，占原始字节的比例）：

| 内容 | 压缩后 |
|---|---|
| 光标、时钟、小片静态区 | 约 **30%** |
| 大段文字滚动（150+ 块） | 约 **52–58%** |
| 照片、视频 | 退回原样（100%） |

全屏 300 块原始 154 KB，压缩后约 62 KB，**整屏换一帧约 115 ms**；
桌面日常使用（打字、切窗口）每次只有几块，几十块以内都能跑满 30 fps，静止时一个字节都不发。

USB-Serial-JTAG 是 12 Mbps 全速设备，实测 550–600 KB/s 就是它的上限（约 45%）：
包大小固定 64 字节，全速总线一帧 1 ms，收包/换包的开销吃掉了一半带宽。
已经试过把 `read_async` 换成阻塞紧循环读（省掉每次收包的唤醒）——瞬时速率没有变化（558 vs 573 KB/s），
所以瓶颈不在驱动，而在这个外设本身。再往上只能减少字节（压缩、降色彩），或者换链路。

想再快就得改成主机侧流水线（不等应答连发），代价是板子要按最坏情况加大接收缓冲、并接受 USB 端点溢出丢数据。

UART0（板载 CH343P）链路：2 Mbaud 线路上限约 196 KB/s，修掉 RX FIFO 溢出后实测 180–190 KB/s
（~250 脏块一帧约 0.36 s）。溢出的坑在 esp-hal：`RxConfig` 默认 `fifo_full_threshold = 120`，
而硬件 FIFO 只有 128 字节，2 Mbaud 下只剩 40 µs 余量；渲染一块 tile 约 200 µs 不让出，
收发一重叠 FIFO 必满，esp-hal 直接 `rxfifo_reset()` 把在途消息整个冲掉且不回 NAK，
上位机表现为每批吃满超时重发、吞吐掉到 ~15 KB/s。固件用 `with_fifo_full_threshold(16)`
把余量放大到 560 µs，重构时别把这行丢了。

## WiFi 链路

`src/main.rs` 顶部三个常量：`SSID = "R3"`、`PASSWORD`、`TCP_PORT = 8080`。换热点改这里重烧，
端口改了两边一起改（上位机 `wifi --port`）。

板子是 TCP **服务端**，地址由 R3 的 DHCP 分，所以每次上电先看 RTT 里这一行拿 IP：

```
INFO  wifi up, tcp server on 192.168.1.23:8080
```

- 一条连接同时只有一条：断开或出错（含 30 s 静默超时）后任务回到 accept，上位机重连即可，不用复位板子
- 读到 `Ok(0)`（对端关流）就退出 `link::serve` 并把手上那块还回槽池；串口链路读错误同样退出、由任务外层重新开始
- WiFi 栈吃 RAM：`HEAP_SIZE = 72 KB` 堆 + `StaticCell<StackResources<3>>`，整套 `.bss` 从 215 KB 涨到 312 KB
  （RAM 段 452 KB），再加大缓冲前先 `size -A` 看一眼
- 板子侧 TCP 收包实测 **393–425 KB/s**（纯收包、1 KB/5 KB/15 KB 消息四种测法一致，约每段 3 ms 唤醒开销），
  与 USB CDC 的 280–600 KB/s 同一量级。scale 1 的 24 fps 只够约 17 KB/帧 ≈ 45 块脏块
- `busy_ms` 报的是**纯绘制**时间（不含等链路）：实测 0.58 µs/像素，全屏 44–47 ms，所以全屏重画最快 21–22 fps

## 运行

```bash
# 板子：烧固件（执行后常驻收帧）
cargo run --release

# 上位机：见 ../secondary-screen-desktop/README.md
cargo run --manifest-path ../secondary-screen-desktop/Cargo.toml -- --verbose
```

`release` 是必须的：dev 构建的 8080 写时序撑不住。

**烧完 probe-rs 会掉线是正常的**：固件一接管 USB-Serial-JTAG，整条 USB 设备会重新枚举，
`cargo run` 的 RTT 会话随之断开，固件继续跑。想一边看 RTT 一边推流，只能改走 UART0 那条链路
（RTT 在 USB-JTAG，数据在 CH343，互不相干）。

RTT 日志：

```bash
probe-rs attach target/riscv32imac-unknown-none-elf/release/ili9341-lcd-secondary-screen --chip esp32c6
```

## 注意

- 三条链路同时开着，但**不要同时跑两个上位机进程**（比如 `serial` 和 `wifi` 各一个）：两边帧号会互相冲突，
  旧帧被当过期丢掉，画面会跳。同时只跑一个。
- 屏的 RST 与板子 EN 共复位，没有独立 GPIO（`NoReset` 空脚顶替），见 `display.rs`。
- 引脚表、`SET_LO`/`SET_HI` 掩码表、`out` 寄存器影子值这些都在 `display.rs`，与 `../ili9341-lcd/` 是同一份实现；
  那边改了要同步过来。
- `MSG` 是 4 KB 的静态缓冲，不放任务栈。
- 主机侧不用管波特率：CDC 是 USB 设备，打开时设的 baud 会被忽略。
- 板子上电不主动清屏之外的动作：第一帧由上位机发满 300 块（`prev` 全 0，全部算脏）。
